# Security

* **Owner-only access.** No public registration exists (no table path, function or endpoint). Owner accounts are created by a developer-run script only after the owner approves.
* **Owner sign-in (implemented, A2): e-mail address and password ONLY, by the owner's decision.** Argon2id password hashes only; a correct password starts a full server-side session at once (random 256-bit token, fresh at every sign-in, in an `HttpOnly; SameSite=Strict` cookie, only its SHA-256 hash stored, 12 h absolute / 30 min idle, revoked on logout, deactivation or role change); lockout after 5 consecutive wrong passwords for 15 minutes; per-address and per-account rate limits; identical answers for unknown / wrong / locked accounts; CSRF protection on three layers (exact dashboard origin, `X-Requested-With` header, per-session token); audit rows for every sign-in, failure, lock-out and logout; new owner passwords must be at least 12 characters. An old half-finished two-step session is never accepted.
* **Accepted risk: no second factor.** Authenticator-app 2FA and recovery codes were removed at the owner's request (2026-11-13). The password is now the only barrier, so a weak or reused password is a real risk: the rate limit and lock-out only slow guessing and cannot stop someone who guesses a common password within a few tries. This is acceptable while everything runs on the owner's own computer (all servers listen on 127.0.0.1 only). Before the dashboard is ever reachable from the internet, choose a long unique password (12+ characters, ideally a passphrase) and reconsider a second factor. The earlier authenticator tables and columns are still in the database, unused, so adding a second factor back later does not lose anything.
* **Credential isolation (implemented, A2):** the public API and the owner API are **separate processes with separate settings files**. The public process holds only the public database login (no table access; it can only call two booking functions); the admin password and both keys exist only in the owner process, and each process refuses to start if it can see the other's secrets. Four independent checks are tested: the database refuses admin functions and tables to the public login over the public API's own connection; the processes' environments are disjoint; nothing reachable from the public entry point imports admin or auth code; neither application serves the other's routes. (An in-process separation could not protect against a flaw in the public code; separate processes can.)
* **Authorization on the server** for every admin action, never only in the UI.
* **API database logins (A2):** the API never connects as an owner or superuser. `newscafe_public` has no table access and can only call two booking functions; `newscafe_admin` can read what the dashboard shows and write only login/session/audit data. All reservation changes go through `SECURITY DEFINER` functions owned by a non-superuser role with a fixed `search_path`; each admin function checks the actor is an active owner, stamps them in the append-only history, and writes the audit row in the same transaction. The audit log never contains guest names, e-mails, phones or notes. Details: [DATABASE.md](DATABASE.md).
* **API process (A2):** fail-closed start-up guards, strict input validation, rate limits, security headers, log allow-list (no personal data or secrets in logs), no stack traces or SQL in errors, exact pinned dependencies with install scripts disabled and `npm audit` clean. A booking is never reported as saved unless the database committed it.
* **Secrets:** never in GitHub. Local `.env` files are git-ignored; production secrets live only in the host's secret store and the owner's password manager. The repository is protected by an allow-list `.gitignore`, a pre-commit check and a gitleaks scan (also in CI).
* **Data separation:** development and staging hold fake data only. Production holds real data and is never reachable from development scripts (see [DATABASE.md](DATABASE.md)). Real data is never copied downwards.
* **Database:** least-privilege application role (A2), parameterised queries, append-only history and audit log, immutable environment label.
* **Uploads:** type and size allow-list (images ≤ 2 MB), resized in the browser, random names.
* **POPIA:** consent timestamp on customer forms, minimal personal data, retention and anonymisation policy, privacy notice (owner to supply). Free plans give no data-processing contract and no South African region; take legal advice before launch.
* **Reporting a problem:** tell the owner immediately; rotate affected secrets (see OWNERSHIP.md offboarding).
